# Authenticate the portfolio control plane

Status: **NOT STARTED — planned 2026-10-25, deferred by Mark (no time that day).**
Priority: hard blocker before `mode=live`. Paper mode it is a sandbox; on live money it is
someone else deciding your positions.

## The problem, verified not assumed (checked 2026-09-25 and again 2026-10-25)

- `GET /api/portfolio/state` returns positions, cash, equity and the entire trade log.
- `GET`/`PUT /api/portfolio/config` read **and write** the desired config. A PUT can remove
  the 30% crypto class cap added on 2026-10-25.
- `POST /api/portfolio/cycle` is guarded only by `PM_CYCLE_TOKEN`, which defaults to empty.
- Both repos (`Mbq24/forge`, `Mbq24/portfolio-manager`) are public, so the DSL and every
  strategy YAML are world-readable.

The edge is not the secret — the condition set is textbook trend-following, and what is
hard here is the measurement discipline. **Control is the thing to protect**, not ideas.

## Design: fail loud, never fail open

    PM_API_TOKEN set     -> require `X-API-Token` on every /api/portfolio/* route
    PM_API_TOKEN unset   -> allow, BUT log a loud warning on EVERY boot and expose
                            `auth: "disabled"` in /health

The second branch is the deliberate choice. "No token means no auth" is convenient locally
and is exactly the fail-open shape that has already cost this stack twice (the swallowed
`TypeError` that closed positions, and the probe that reported `ok: true` from its silent
fallback). A missing token in production must be **visible**, not permissive-and-quiet.
Reporting it in `/health` lets monitoring alarm on it — deliberate inaction becomes its own
reported condition.

Unify with the existing `X-Cycle-Token` pattern rather than inventing a second mechanism:
one token, one header name, checked on every portfolio route in **both** services (read
routes too, not just writes).

## Local dev — full auth, no divergence

Token lives in `.env`, already gitignored in both repos. Both services load it, so local
runs exercise the same code path as production instead of a permissive variant.

    curl -H "X-API-Token: $PM_API_TOKEN" localhost:5000/api/portfolio/state

Tests use the Flask test client — no network, no server: one asserts 401 without the header,
one asserts 200 with it.

## Blast radius — every one of these must send the header

Ten callers, found by grepping `api/portfolio` across `~/.hermes/scripts`, both repos:

    ~/.hermes/scripts/forge_daily_digest.py
    ~/.hermes/scripts/forge_strategy_probe.py
    ~/.hermes/scripts/morning_briefing.py
    ~/.hermes/scripts/trade_alert_remote.py
    ~/.hermes/scripts/verify_forge_pm_tick.py
    portfolio-manager/briefing.py
    portfolio-manager/check_forge_state.py
    portfolio-manager/run.py            (pm -> Forge: sync config, push state)
    portfolio-manager/portfolio_server.py
    Forge/tradingview/app.py

**The failure mode to design against is silence.** Miss one consumer and it fails quietly —
which is precisely how the briefings went dark for 33 hours in October.

## Rollout order (auth must land everywhere at once, or briefings break)

1. Shared header helper + the fail-loud flag, in portfolio-manager.
2. Flask tests: 401 without header, 200 with, `auth: "disabled"` surfaced when unset.
3. Wire Forge's routes the same way.
4. Wire the five cron scripts.
5. Set the token in **both** Railway services and in the local env used by cron. Note: cron
   runs inside the gateway process, so it inherits the gateway's environment — confirm it
   can actually see the token before relying on it.
6. Deploy both, then verify EACH consumer explicitly:
   - `POST /api/portfolio/cycle` still runs
   - `trade_alert_remote.py` still reports (or stays correctly silent)
   - `forge_daily_digest.py` / `forge_briefing_fallback.py` still deliver
   - `/health` reports `auth: "enabled"`, not `"disabled"`
7. Only then set `mode=live`.

Effort estimate: ~half a day, mostly mechanical.
